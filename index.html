Design notes and open questions

Remediation presentation (for later)

  • Rank by risk-adjusted priority: known-exploited (KEV) status weighted over raw CVSS.
  • Each finding as a card: what is affected, why it matters, the fix, effort estimate.
  • Split "patch available" from "no patch yet" (needs compensating controls).
  • Group by remediation owner / root cause, not by host.
  • Track findings across scans over time.

Open design question

Should each attack-surface branch hold a static reference set of common CVEs (a general knowledge tree), or should CVEs populate only once a real scan runs against a real client asset (a live, per-engagement tree)?

Static reference treeReusable framework, good for training and scoping, goes stale as new CVEs appear.
Live per-engagement treeAlways current and client-specific, but rebuilt every time.
Hybrid (worth considering)Static tree for asset types and attack surfaces (they change slowly); CVEs and patches fed live from NVD/vendor data per scan.
